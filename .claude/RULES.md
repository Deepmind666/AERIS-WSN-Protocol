# AERIS-WSN-Protocol 项目规则（Claude 专用）

**优先级**: 本规则 > 系统级 `AI_COLLAB_RULES.md`

---

## 语言规则（强制，最高优先级）

1. **必须全程使用中文**与用户沟通。包括但不限于：报告、审查清单、进度更新、问题确认、错误说明、任务规划等所有输出。
2. **compact / 上下文恢复后**也必须继续使用中文，不得切换为英文。每次 compact 恢复后的第一条输出必须是中文。
3. **代码注释**：新增或修改的代码注释使用中文（已有英文注释不强制翻译）。
4. **文档与报告**：所有面向项目内部的 .md 文档使用中文撰写。仅论文正文（英文期刊投稿）和 NS-3 C++ 源码注释使用英文。
5. **违反后果**：如果 Claude 输出英文，用户有权要求立即重做，且该输出视为无效。

---

## 资源利用优先级规则（强制）

1. **用户明确要求 > SOP 默认值**：用户要求加大/降低利用率时，立即执行，无需与 SOP 对齐。
2. **无特殊要求时**：正常运行，保证设备不会因内存爆炸或进程爆炸导致故障。
3. **用户不使用设备时**（如睡觉）：可拉满利用率，但不得导致设备因进程/内存爆炸而故障。

---

## 0. 修改前审批（强制）
- 任何修改（代码/文档/配置/结果）前，必须先输出：**路径 + 计划 + 影响范围**，并等待用户批准。

## 1. PDR 口径定义（强制）

| 指标 | 公式 | 用途 |
|------|------|------|
| **pdr_expected** (主指标) | `bs_delivered / source_packets_expected` | 论文报告、协议对比 |
| pdr_attempted (副指标) | `bs_delivered / source_packets_attempted` | 诊断分析 |
| pdr_raw_attempted | 协议原始返回值 | 仅供溯源 |

**禁止** 使用未定义的 `pdr` 字段，必须明确口径。

---

## 2. 实验参数规范（强制）

### 2.1 基准默认值（诊断/基线）
- `tx_power_dbm = 10.0`
- `environment = indoor_office`
- `num_nodes = 100`
- `num_rounds = 300`
- `area = 200m × 200m`
- `base_station = (100, 200)`

### 2.2 正式实验矩阵（发布/对比）
- 明确列出 **node_counts / round_counts / dropout_rates / environments / tx_powers**
- **必须**在结果 JSON 的 `config` 字段中完整记录

---

## 3. 统计要求（强制）
- **publication 级别**：`n ≥ 30 seeds (42001–42030)`
- **diagnostic 级别**：允许 n < 30，但必须标注 `run_tier=diagnostic`
- **报告格式**：`mean ± std`，必须标注样本规模与适用范围
- **禁止外推**：特定场景结论不可泛化为全局

---

## 4. 结果元数据必填（强制）

每个 JSON 结果文件必须包含：

```json
{
  "timestamp": "YYYYMMDD_HHMMSS",
  "git_commit": "8-char hash",
  "experiment_type": "fair_5protocol | power_sensitivity | env_sensitivity | ablation | ...",
  "run_tier": "diagnostic | publication",
  "primary_metric": "pdr_expected",
  "environment": "indoor_office | multiple",
  "tx_power_dbm": 10.0 | "multiple",
  "config": {
    "seeds": [..],
    "node_counts": [..],
    "round_counts": [..],
    "dropout_rates": [..]
  },
  "raw_results": [ ... ]
}
```

**特殊值 "multiple" 说明**：
- `environment: "multiple"` — 用于环境敏感性实验，具体环境列表记录在 `config.environments`
- `tx_power_dbm: "multiple"` — 用于功率敏感性实验，具体功率列表记录在 `config.tx_powers_dbm`

**元数据补齐规则**：允许补齐，但必须新生成文件并附加：
- `patched_from`: 原文件名
- `patch_note`: 补齐说明

**诊断类例外**：`run_tier=diagnostic` 的实验允许 `primary_metric` 非 `pdr_expected`，但必须附加 `metric_note` 字段说明原因。

---

## 5. 消融实验诊断要求（强制）
必须记录以下诊断字段：
- `diag_flags`：模块开关状态
- `diag_cas_modes`：DIRECT/CHAIN/TWO_HOP 计数
- `diag_safety_overrides`
- `gateway_uplink_attempts / gateway_uplink_success`
- `skeleton_backbone_size / skeleton_assignments`
- `cas_total_decisions`

`hasattr()` 仅可作为“对象创建”证据，**不得**作为“模块生效”证据。

- 必须记录 **seed/拓扑/能耗模型** 与 Python 对齐状态

## 9. GitHub 操作规范（本项目专用，强制）

1. 服务器实验只能基于 **已 push commit** 执行，禁止使用本地未提交代码。
2. 每次实验回报必须包含：
   - `git_commit`
   - `git_dirty`
   - `git_diff_stat`
   - `script_sha256`
3. 禁止强推（force push）覆盖共享历史；默认 `commit + push`。
4. 启动服务器实验前，必须先给出：
   - 目标 commit hash
   - 运行命令
   - 预计耗时与资源上限

## 10. 代码注释与架构要求（本项目专用，强制）

1. 注释必须解释“逻辑依据/科研依据”，不能写空洞描述。
2. 关键算法分支必须注明：
   - 触发条件
   - 统计口径
   - 与论文结论的对应关系
3. 新增实验脚本必须包含：
   - 参数说明
   - 资源限制策略（CPU/MEM）
   - 完整性校验（raw_results 计数、error_runs）

4. 禁止编造结论；不确定项必须标注“证据不足”。

## 12. NS-3 强制门槛（本项目专用，强制）

### 12.1 禁止误用
- 未满足本节全部条件时，禁止写“NS-3 数值级验证完成”。
- 只能写 “trend-level validation”。

### 12.2 最低通过条件
1. 参数对齐：`environment / tx_power_dbm / initial_energy / rounds / packet_size / seeds` 全部对齐。
2. 样本规模：核心场景 `n >= 30` 且 seeds 显式记录。
3. 证据链：必须有 JSON 原始结果 + 统计检验 + 对齐说明文档。
4. 阈值建议：PDR 差异 <=5%，能耗差异 <=10%（仅在模型完全一致时适用）。

### 12.3 交付文件
- `ns3_validation/results/NS3_ALIGNMENT_EVIDENCE.md`
- `ns3_validation/results/ns3_*_publication*.json`
- 对应显著性统计文件（Welch + Hedges g + Holm）

## 16. 上下文管理（强制，防止 context overflow）

### 16.1 文件读取纪律
- 禁止一次性读取整个代码库或大量文件进行"onboarding"。
- 每次只读取与当前任务直接相关的文件，优先用 `Grep`/`Glob` 定位后再精确读取。

### 16.2 增量输出
- 审计/检查类任务的发现必须即时写入磁盘文件（如 `audit_results.md`），禁止在对话中累积大量中间结果。

### 16.3 会话拆分意识
- 若预判当前任务可能超出上下文容量（如 >10 个文件的审计、全量重跑分析），主动建议用户拆分为多个会话。
- 每个会话结束前，将未完成事项写入 `docs/handoff_YYYYMMDD.md`，供下次会话恢复。

## 17. 代码编辑安全（强制）

### 17.1 现有文件保护
- 修改 `src/` 下的任何 `.py` 文件前，必须先说明修改计划并获得用户批准。
- 禁止在未经确认的情况下重构、重命名或删除现有工作代码。
- 实验性修改必须创建新文件（如 `xxx_v2.py`），不得直接覆盖原文件。

### 17.2 最小化修改原则
- 只修改与当前任务直接相关的代码，禁止"顺手"重构周边代码。
- 禁止添加用户未要求的 docstring、类型注解、注释美化。
- bug 修复只改 bug 本身，不改周围代码风格。

### 17.3 结果文件保护
- `results/` 和 `ns3_validation/results/` 下的 JSON/CSV 文件禁止直接修改。
- 需要修正时，生成新文件并附 `patched_from` + `patch_note`。

## 18. 任务执行纪律（强制）

### 18.1 方向确认
- 收到任务后，先用 1-2 句话复述理解，确认方向正确后再动手。
- 若任务涉及多个可选方案，必须列出方案并等用户选择，禁止自行决定。

### 18.2 范围控制
- 严格执行用户指定的任务范围，禁止自行扩展 scope。
- 用户说"修复 A"，只修复 A，不要"顺便"改 B/C/D。
- 用户说"检查 X 文件"，只检查 X，不要扫描整个目录。

### 18.3 错误恢复
- 同一操作连续失败 2 次后，必须停下来向用户说明情况和替代方案，禁止盲目重试。
- SSH 连接失败时，先检查是否使用了正确的别名（§15），再报告问题。

### 18.4 任务完成确认
- 每个任务完成后，给出交付物清单（文件路径 + 简要说明），不超过 5 行。
- 禁止冗长的总结回顾，用最少文字说明完成了什么。

## 20. Shell 命令规范（Windows 环境）

### 20.1 本地环境
- 本地 shell 为 bash（Git Bash），使用 Unix 语法（正斜杠、`/dev/null`）。
- 路径中有空格时必须用双引号包裹。

### 20.2 远程环境（FatMachine）
- FatMachine 默认 shell 为 CMD，PowerShell 命令需用 `powershell -NoProfile -Command "..."` 包裹。
- SSH 传递命令时，`$` 符号会被本地 bash 解释，需用单引号或转义。
- `scp` 路径必须使用正斜杠，否则报 `unexpected EOF`。

### 20.3 禁止事项
- 禁止使用 `nohup`、`start /B`、`Start-Process` 等不可靠的后台运行方式（SSH 断开后进程会被终止）。
- 禁止在 SSH 远程命令中使用 `conda activate`，必须用完整 Python 路径。

## 21. 多 Claude 协作规范（强制）

### 21.1 进程保护
- 禁止对服务器执行 `taskkill /F /IM python.exe` 等批量杀进程操作，除非用户明确指定 PID。
- 操作服务器进程前，必须先用 `tasklist` 或 `Get-CimInstance` 确认目标进程的命令行和归属，区分实验进程与后台服务进程。
- 若需终止进程，必须逐 PID 操作并记录原因，禁止通配符批量终止。

### 21.2 共享资源意识
- 服务器上可能同时运行多个 Claude 实例的任务。操作前必须检查是否有其他实验正在运行（检查日志尾部、Python 进程数、PowerShell 进程数）。
- 发现有正在运行的实验时，禁止启动新的高资源任务，必须先向用户确认。
- 禁止修改或删除其他 Claude 实例创建的文件（日志、JSON 结果、脚本），除非用户明确授权。

### 21.3 实验归属标记
- 每个实验脚本的日志文件名必须包含唯一时间戳（`YYYYMMDD_HHMMSS`），避免多实例日志冲突。
- 启动实验时，在日志首行记录：启动者身份（如 `claude-session-xxx`）、任务名称、预计耗时。

## 22. 服务器实验容错与队列（强制）

### 22.1 中断恢复
- 实验脚本必须设计为可中断恢复：每个阶段完成后写入阶段标记（如 `FILL-1 done: exit=0`），补跑脚本可据此跳过已完成阶段。
- 若实验被意外中断（exit≠0），必须检查输出 JSON 是否存在且完整（文件存在 + `raw_results` 计数正确），而非仅依赖 exit code。

### 22.2 队列脚本规范
- 需要排队执行的任务，必须创建独立的队列脚本（如 `*_retry.ps1`），通过轮询日志标记等待前序任务完成。
- 队列脚本必须包含：
  1. 等待逻辑（轮询间隔 ≥ 60 秒）
  2. 前序完成验证
  3. 核心任务执行
  4. 输出文件存在性校验
  5. 后处理自动触发（若适用）
- 队列脚本的日志必须独立于主 bundle 日志，便于分别追踪。

### 22.3 SSH 超时应对
- 本地 SSH 后台任务有 10 分钟超时限制。长时间实验（>10 分钟）的 SSH 连接会断开，但服务器端 PowerShell 进程不受影响。
- 禁止将 SSH 超时断开误判为实验失败。判断实验状态的唯一依据是服务器端日志内容和进程列表。
- 检查实验状态时，优先读取日志关键标记（`findstr` 搜索阶段标记），其次检查进程列表，最后检查输出文件。

## 23. 审计与检查输出规范（强制）

### 23.1 首轮交付原则
- 审计/检查类任务必须在第一轮即产出具体发现，附带 `文件:行号` 引用。
- 禁止先做多轮"探索性阅读"再输出发现。边读边产出，即时落盘。
- 若审计范围超过 5 个文件，必须使用 Task 子代理分文件并行审计，主会话只做汇总。

### 23.2 发现分级
- 每条发现必须标注严重级别：
  - **P0**：阻塞发布（数据错误、统计方法错误、禁止声明残留）
  - **P1**：应修复（格式不一致、引用缺失、表述模糊）
  - **P2**：建议改进（可读性、风格）
- 输出格式：`[P0] 文件:行号 — 问题描述`

### 23.3 增量落盘
- 审计发现必须即时写入磁盘文件（如 `docs/audit_YYYYMMDD.md`），每处理完一个文件立即追加写入。
- 禁止在对话中累积超过 20 条发现后才落盘。
- 会话结束或 compact 前，必须确认所有发现已落盘。

## 24. 上下文预算管理（强制）

### 24.1 产出优先原则
- 每个会话的上下文预算中，产出（代码编写、文件生成、审计报告）必须占主体，探索（文件读取、搜索）不得超过总预算的 40%。
- 若探索阶段已消耗大量上下文但尚未开始产出，必须立即停止探索，基于已有信息开始产出，并标注"基于部分信息，可能不完整"。

### 24.2 大文件读取限制
- 单个 JSON 结果文件（>1MB）禁止全量读取到对话中。使用 `python -c` 或 `jq` 提取所需字段。
- 读取代码文件时，优先用 `Grep` 定位目标行，再用 `Read` 读取目标行 ±20 行范围，禁止无目的全量读取。

### 24.3 子代理分流
- 以下任务类型必须使用 Task 子代理，禁止在主会话中直接执行：
  1. 跨 >3 个文件的搜索/审计
  2. 代码库结构探索（"这个项目怎么组织的"）
  3. 大规模 grep/glob 扫描
- 子代理返回结果后，主会话只引用摘要，不重复展示原始内容。

### 24.4 compact 前检查点
- 预感上下文即将耗尽时（如已处理 >8 个文件、对话轮次 >15），主动将当前进度和未完成事项写入 `docs/handoff_YYYYMMDD.md`。
- 检查点文件必须包含：已完成事项、未完成事项、关键发现、下次会话的建议起点。

## 25. 回答质量纪律（强制）

### 25.1 先想后答
- 回答前先想清楚，不要急着输出。宁可先问用户两个关键问题，也不要给一堆正确的废话。
- 要的是具体、能用、针对当前情况的答案，不是放之四海皆准的建议。

### 25.2 全能力调用
- 回答时先翻对话记忆有没有相关背景，能联网就搜，能写代码就写，把所有可用能力都用上。
- 禁止在有工具可用时只给文字建议。

### 25.3 不满意时换思路
- 用户说不满意，不要只换个说法重复，必须换个思路重新想。
- 同一方案被否决后，下次必须给出本质不同的替代方案。

## 26. 服务器实验自动推进流程（强制）

### 26.1 串行队列执行模式
- 服务器实验按预定义队列串行执行，每个任务完成后自动启动下一个。
- 禁止并行启动多个重负载实验（除非用户明确授权且服务器资源充足）。
- 队列定义必须在启动前明确列出，包含：任务编号、环境、参数、输出文件名。

### 26.2 SSH 断开重连规则
- SSH 后台任务超时（通常 10 分钟）后，必须主动重连检查状态。
- 重连检查顺序：
  1. 检查输出 JSON 文件是否存在（`if exist ... echo FILE_EXISTS`）
  2. 若文件存在，验证完整性（`raw_results` 计数 + `error_runs` + `run_tier`）
  3. 若文件不存在，检查进程列表（`tasklist /FI "IMAGENAME eq python.exe"`）
  4. 若进程仍在运行，读取日志尾部获取进度
- SSH 连接失败时，等待 2-3 分钟后重试，最多重试 3 次。超过 3 次报告用户。
- 禁止将 SSH 超时或网络波动误判为实验失败。

### 26.3 任务验收标准（逐任务）
- 每个任务完成后必须验证以下 4 项全部通过才算验收：
  1. `raw_results` 计数 == 预期值（如 30000）
  2. `error_runs` == 0
  3. `run_tier` == `publication`
  4. `primary_metric` == `pdr_expected`
- 验收失败的任务必须记录失败原因，并决定：重跑 / 跳过并标注 / 报告用户。
- 验收通过后立即启动下一个任务，不等待用户确认（用户已授权自动推进时）。

### 26.4 后台执行与日志
- 服务器实验必须将 stdout 重定向到日志文件（`> logfile 2>&1`）。
- 日志文件命名：`s10r_{env}_{tx}.log`，与输出 JSON 同目录。
- 使用 `run_in_background` 启动 SSH 命令，避免阻塞主会话。

## 27. 吞吐基准与 ETA 校准（强制）

### 27.1 已知吞吐基准（S10R 实验，2026-02-26 实测）

| 机器 | workers | 稳态速率 | 单任务耗时（30000条） |
|------|---------|----------|----------------------|
| 服务器 (5090) | 20 | 45-55/s | 9-12 min |
| 本地 (Win11) | 默认 | 3.5-4.0/s | 125-145 min |

### 27.2 ETA 计算规则
- 首次 ETA 必须基于实测吞吐（至少观察 500 条后的稳态速率），禁止凭经验猜测。
- ETA 必须给区间（如 `9-12 min`），不给点估计。
- 串行队列总 ETA = 单任务耗时 × 剩余任务数 + 当前任务剩余时间。
- 每次汇报 ETA 时必须注明依据（如"基于最近 1000 条的速率 50/s"）。

### 27.3 跨机器对比
- 本地与服务器吞吐差异可达 10-15 倍，禁止用一方的速率估算另一方的 ETA。
- 多实例并行时，总墙钟取慢侧（瓶颈机器）。

## 28. 多实例协作分工规范（强制，§21 升级版）

### 28.1 角色边界
- 每个 Claude/Codex 实例在会话开始时必须明确自己的角色边界：
  - **服务器实例**：只操作 FatMachine，只产出 `results/mega_experiments/` 和 `docs/` 下文件
  - **本地实例**：只操作本地机器，不 SSH 到服务器执行实验
- 禁止越权操作对方负责的机器或文件范围。

### 28.2 交接文档规范
- 多实例并行任务必须有交接文档（`docs/YYYYMMDD_*_handoff.md`），包含：
  - 各实例的任务分配
  - 执行参数（完整命令模板）
  - 验收标准
  - 后处理入口脚本
- 交接文档由发起方创建，执行方只读不改。

### 28.3 结果合并时序
- 多实例产出的结果文件，合并操作由最后完成的一方执行。
- 合并前必须确认所有分片文件均已通过验收（§26.3 四项标准）。
- 合并脚本必须预先准备好（如 `scripts/postprocess_s10r_4env.py`），禁止临时编写。

### 28.4 冲突预防
- 禁止两个实例同时写入同一文件。
- 输出文件名必须包含机器标识（如 `_server_` / `_local_`）以避免命名冲突。
- git 操作（commit/push）由用户指定的实例执行，另一方禁止自行 push。

## 29. 投稿包同步规范（强制，2026-03 新增）

### 29.1 双目标架构
- 论文有两个编译目标：
  - `for_submission/AERIS_Sensors_MDPI_Submission_Draft_*.tex`（开发版，长文件名图表）
  - `AERIS_Sensors_Submission/manuscript.tex`（投稿版，短文件名 fig1-fig10）
- 两者文本必须完全一致（排除 `\graphicspath` 和 `\includegraphics` 路径差异），TEXT DIFF=0。

### 29.2 图表同步规则
- 图表映射关系记录在 `CLAUDE.md` 的"投稿包图表映射"部分。
- 每次修改图表生成脚本并重新生成后，必须：
  1. 将所有受影响的 PDF 复制到 `AERIS_Sensors_Submission/figures/figN.pdf`
  2. 用 MD5 校验全部 10 张图一致性（不能只验单张）
  3. 若脚本同时生成多张图（如 s98 同时生成 fig2 和 fig6），所有图都必须同步
- 禁止投稿包中出现未同步的旧图。

### 29.3 文本同步规则
- 修改 v*.tex 后，必须将相同文本变更应用到 `manuscript.tex`。
- 同步后必须分别编译两个目标并验证页数一致。
- 推荐用 `diff <(pdftotext v98.pdf -) <(pdftotext manuscript.pdf -)` 验证文本差异。

### 29.4 统计值报告规则（P0 级）
- 论文中报告 p 值时，必须明确标注类型：`p_Holm`（校正后）或 `p_raw`（校正前）。
- 禁止将 raw p 值误标为 Holm-corrected p 值。
- 每个比较 family 的 m 值必须在方法节或首次使用处明确声明。
- 修改 p 值后，必须用脚本从原始数据重算验证。
